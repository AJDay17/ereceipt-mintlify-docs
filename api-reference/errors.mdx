When a request to the E-Receipt API fails, the response body contains a structured error object that tells you exactly what went wrong and, where relevant, which request parameter caused the problem. Building robust error handling around this format helps your integration recover gracefully and surface actionable messages to your users.

## Error Response Format

All error responses share the same envelope:

```json
{
  "error": {
    "code": "invalid_customer",
    "message": "No customer found with id cus_abc123",
    "param": "customer_id"
  }
}
```

The three fields in the error object are:

| Field | Type | Description |
|---|---|---|
| `code` | string | A machine-readable identifier for the error type. Use this in your code to branch on specific failure cases. |
| `message` | string | A human-readable explanation of the error. Suitable for logging; use with care before surfacing directly to end users. |
| `param` | string \| null | The name of the request parameter that caused the error, if the error is tied to a specific field. `null` for general errors. |

## HTTP Status Codes

E-Receipt uses standard HTTP status codes to indicate the outcome of every request.

| Status | Meaning |
|---|---|
| `200 OK` | The request succeeded. The response body contains the requested resource. |
| `201 Created` | A new resource was successfully created. The response body contains the new resource. |
| `400 Bad Request` | The request was malformed or contained invalid parameters. Check the `param` field for the offending input. |
| `401 Unauthorized` | The request did not include an API key, or the key is invalid or revoked. |
| `403 Forbidden` | The API key is valid but does not have permission to perform the requested action. |
| `404 Not Found` | The requested resource does not exist, or the endpoint path is incorrect. |
| `409 Conflict` | The request conflicts with an existing resource — for example, reuse of an idempotency key with a different request body. |
| `422 Unprocessable Entity` | The request was well-formed but failed validation rules. Check the `message` and `param` fields for details. |
| `429 Too Many Requests` | You have exceeded the rate limit of 100 requests per minute. Wait before retrying. |
| `500 Internal Server Error` | An unexpected error occurred on the E-Receipt servers. If this persists, contact support. |

## Error Codes Reference

The following table lists all `code` values you may encounter, grouped by category.

| Code | HTTP Status | Description |
|---|---|---|
| `missing_api_key` | `401` | No `Authorization` header was present in the request. |
| `invalid_api_key` | `401` | The API key is malformed, expired, or has been revoked. |
| `insufficient_permissions` | `403` | The API key does not have permission for this operation. |
| `invalid_customer` | `400` | The customer data provided is malformed or fails validation. |
| `customer_not_found` | `404` | No customer exists with the given ID. |
| `invalid_receipt` | `400` / `422` | The receipt payload is malformed or fails validation rules. |
| `receipt_not_found` | `404` | No receipt exists with the given ID. |
| `receipt_already_sent` | `409` | The receipt has already been delivered and cannot be modified or resent in this way. |
| `invalid_template` | `400` / `422` | The template reference is invalid or the template data fails validation. |
| `template_not_found` | `404` | No template exists with the given ID. |
| `delivery_failed` | `500` | The receipt was created but the delivery attempt failed. You can retry delivery. |
| `invalid_email` | `422` | The email address provided is not a valid format. |
| `invalid_phone` | `422` | The phone number provided is not a valid format. |
| `rate_limit_exceeded` | `429` | You have sent too many requests. Back off and retry after a short delay. |
| `server_error` | `500` | An unexpected internal error occurred. Retry with exponential backoff or contact support. |

## Handling Errors in Code

Check the HTTP status code first, then inspect the `error.code` field to branch your logic for specific failure cases.

<CodeGroup>

```javascript JavaScript
async function createReceipt(payload) {
  const response = await fetch('https://api.e-receipt.com/v1/receipts', {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${process.env.ERECEIPT_API_KEY}`,
      'Content-Type': 'application/json'
    },
    body: JSON.stringify(payload)
  });

  const data = await response.json();

  if (!response.ok) {
    const { code, message, param } = data.error;

    switch (code) {
      case 'invalid_api_key':
        throw new Error('API key is invalid. Check your credentials.');
      case 'customer_not_found':
        throw new Error(`Customer not found. Check the value of '${param}'.`);
      case 'rate_limit_exceeded':
        throw new Error('Rate limit hit. Retry after a delay.');
      default:
        throw new Error(`API error [${code}]: ${message}`);
    }
  }

  return data;
}
```

```python Python
import os
import requests

def create_receipt(payload):
    response = requests.post(
        'https://api.e-receipt.com/v1/receipts',
        headers={
            'Authorization': f"Bearer {os.environ.get('ERECEIPT_API_KEY')}",
            'Content-Type': 'application/json'
        },
        json=payload
    )

    data = response.json()

    if not response.ok:
        error = data.get('error', {})
        code = error.get('code', 'unknown')
        message = error.get('message', 'An unknown error occurred.')
        param = error.get('param')

        if code == 'invalid_api_key':
            raise ValueError('API key is invalid. Check your credentials.')
        elif code == 'customer_not_found':
            raise ValueError(f"Customer not found. Check the value of '{param}'.")
        elif code == 'rate_limit_exceeded':
            raise RuntimeError('Rate limit hit. Retry after a delay.')
        else:
            raise RuntimeError(f"API error [{code}]: {message}")

    return data
```

</CodeGroup>

## Rate Limit Handling

When you receive a `429 Too Many Requests` response, pause before retrying. Use exponential backoff — increasing the delay with each successive retry — to avoid hammering the API and prolonging the wait.

```javascript
async function fetchWithBackoff(url, options, maxRetries = 4) {
  let attempt = 0;

  while (attempt <= maxRetries) {
    const response = await fetch(url, options);

    if (response.status !== 429) {
      return response;
    }

    if (attempt === maxRetries) {
      throw new Error('Rate limit exceeded. Max retries reached.');
    }

    // Exponential backoff: 500ms, 1s, 2s, 4s, ...
    const delayMs = 500 * Math.pow(2, attempt);
    console.warn(`Rate limited. Retrying in ${delayMs}ms (attempt ${attempt + 1})...`);
    await new Promise(resolve => setTimeout(resolve, delayMs));

    attempt++;
  }
}
```

<Note>
  Use **idempotency keys** to safely retry `POST` requests without the risk of creating duplicate resources. Include a unique `Idempotency-Key` header on any request you may need to retry — E-Receipt will return the original response if the same key is received a second time within 24 hours. Generate idempotency keys using a UUID (v4) or another collision-resistant identifier.

  ```bash
  curl -X POST https://api.e-receipt.com/v1/receipts \
    -H "Authorization: Bearer erecp_live_abc123..." \
    -H "Idempotency-Key: a1b2c3d4-e5f6-7890-abcd-ef1234567890" \
    -H "Content-Type: application/json" \
    -d '{"customer_id": "cus_abc123", ...}'
  ```
</Note>
